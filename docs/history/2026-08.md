  - 现象：Hermes（MCP Python SDK，Streamable HTTP 传输）调用工具偶发挂起至 300s tool_timeout（实测 `get_weekly_report` 300.02s 超时）；**同刻 curl 直连 `:8799/mcp` 完全正常**（13.2s 返回）——排查迷惑点

### 2026-08-21 · fix(notify): 修复 webhook 异步通道 rejection 逃逸导致进程崩溃（审核实测复现）

- **根因**：`core/notifier.js` 的 `_dispatch` 用同步 `try/catch` 调用通道，但 `makeWebhookChannel` 返回 async 函数——fetch 失败（网络不可达/超时/非 2xx）时 Promise reject，同步 catch 捕获不到 → unhandled rejection → Node 15+ 默认 throw 模式**直接终止进程**。webhook 是外部网络通道、最易失败，失败时反而带崩无人值守服务，与「通道失败静默吞掉」设计相反
- **修复**：`_dispatch` 内对通道返回值做 Promise 兼容——`ret.catch(...)` 挂 rejection 处理（async 通道）；同步通道返回 undefined 不受影响。审核建议的两种方案取更通用的一种（对任何未来 async 通道生效）
- **顺手改进（审核 🟡 建议）**：needsTotp/recovered 状态跳变型也受 `min_interval_sec` 限制——3 处接线（启动/WS/运行期 401）文案不同，同一故障流短时间多次不同文案通知会刷屏，统一间隔约束
- **实测**：模拟审核复现（async 通道 throw + 真实 webhook 到不可达地址）→ 进程不再崩溃，rejection 被捕获记日志；去抖改进（状态跳变间隔/同消息去重/聚合阈值）全部通过

## 2026-08-21 · fix(plugin): vrc_restart 假成功不重启（commit 06bf4cb，直推 main）

- 根因（两层）：① restart() 用 try/except 吞掉 stop() 失败（stop 返回 ok:False 不抛异常），start() 探测到服务还在运行就返回 already_running——**代码变更从不生效但看起来成功**；② stop() taskkill 后只等 3 秒不验证进程是否真退出，进程仍存活也返回 ok:True（假成功），restart() 等端口循环跑满后无条件 start()
- 修复（hermes-plugin/process_manager.py，+88/-9）：stop() taskkill 后检查 `_pid_alive`，进程仍存活返回 ok:False + 明确错误；restart() 等端口循环改 for-else，health probe 持续响应（旧进程没死）即返回错误中止，不再调 start() 造成 already_running 假象；`_find_monitor_pid()` 升级为 netstat（127.0.0.1:8799 LISTENING 定位 pid）+ wmic 命令行匹配**双方法**，解决 inferred 状态（.active.json 无 pid）定位不到真实 pid；stop() 在 state 文件缺失时也尝试定位真实 pid
- 兜底：state 缺失 + 探测到服务在跑但定位不到 pid 时，明确报「请手动 taskkill 或重启 Hermes」，不静默返回成功

**演进意义**：**运维动作的「效果验证」原则**——服务管理命令不能只看命令本身执行了没有，必须验证命令的**效果**（stop 要确认进程真死、restart 要确认旧进程确实退出后才启动新的）；「假成功」比「失败」更危险：失败会报警，假成功会让用户以为代码变更已生效而实际从未重启，问题被长期掩盖。确立 **进程管理双向验证**（kill 后验证死、启动前验证端口释放）+ **失败必须显式中止**（restart 任一步失败不继续伪装成功）的健壮性模式，状态文件缺失时用端口监听兜底定位真实进程。
